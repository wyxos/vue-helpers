# Security automation proposal

Status: **inactive**. `policy.json` is a proposed contract, not a running updater. No task, workflow, GitHub setting, allowlist entry, credential, default-branch integration or release is created by these files. The current authorization to push the tested isolated branch does not authorize future unattended pushes.

Use a local job on NOVA, initially scheduled only to report. Its first phase reads the default-branch manifest/lock, open GitHub advisories, full `npm audit --json` and production `npm audit --omit=dev --json`. It records advisory IDs, affected package paths, dependency scope, patched versions and the minimum compatible update. It must report registry/authentication errors as errors. Do not assign alerts to GitHub agents: that can also create a draft PR.

[Dependabot security updates](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-security-updates) generate PRs. The proposed local job avoids that feature and never opens a PR. It does not disable any existing setting or dismiss alerts.

## Updates that can eventually qualify

Only a reviewed, development-only transitive utility, updated within the **same resolved major and minor**, with every existing parent range satisfied. Every changed lockfile path needs its own allowlist entry, advisory ID, reviewed version bounds and regression test. The allowlist starts empty, so **no update currently qualifies for unattended application**.

Potential classes to review are ANSI escape handling, argument parsing and text wrapping: for example a future `ansi-regex` 5.0.x patch, `minimist` 1.2.x patch or `word-wrap` 1.2.x patch. These are examples of eligibility, not approval of a version. They must be absent from the production/peer tree and all gates below must pass. A transitive dependency marked `dev` is not sufficient evidence by itself; confirm consumer resolution and all paths. Release notes, changed install scripts, engine requirements and security impact must be reviewed before approving an allowlist entry.

Always review runtime/peer updates; pre-1.0 minor or any major change; new or removed package paths; override/range/registry changes; compiler, loader, minimizer, polyfill and CSS build changes; and development-server/certificate/crypto behavior. This includes the present Axios 0.x change, the scoped `selfsigned`/`node-forge` override, the webpack 4 update, and any Mix 5 to 6 or Vue 2 to 3 migration. Same-range lockfile refreshes performed during this task are manually reviewed work, not blanket future approval. Severity alone does not establish compatibility.

## Required gates

1. Create a new clean worktree at the recorded default-branch SHA. Preserve every existing checkout. Use a verified pinned Node/npm pair and the same install options for baseline and candidate. Serialize installs/builds and install with `npm ci`; require the lockfile to remain unchanged. Run dependency lifecycle code only in this disposable environment without release or write credentials.
2. Limit the source diff to `package-lock.json`; leave runtime/peer resolution, manifests, overrides, package version, scripts, source, exports and build configuration unchanged. All changed paths must be reviewed allowlist entries with patch-only version increases. Reject unrelated churn, added/removed paths, integrity/registry anomalies and changed package lifecycle/engine requirements. Verify all parent ranges, not merely the root range. Inspect build output changes and the packed file list separately.
3. Fetch baseline and candidate audit reports together using the same registry and tool version. The target advisory must disappear at **every** affected path. Reject any new advisory ID, newly affected path or increased severity, even when the total count drops. The production report must not regress. Preserve existing unresolved advisories with their IDs and reasons; never reinterpret them as clean or dismiss them. Refresh the reports immediately before a remote write.
4. Run `npm run production`, `npm test`, then `npm run development`. Building production first ensures the UMD consumer test exercises freshly built output. Run `npm run lint:check` without `--fix`; require no new diagnostics against a captured baseline. Existing lint debt does not make a new failure acceptable. Require a regression test for the behavior implicated by the advisory. This repository currently has no TypeScript/type-check script; do not claim a type check ran.
5. Validate the production bundle before the development build can overwrite artifacts. Pack the library without publishing, inspect its files, then install that tarball into clean consumer fixtures using Vue 2.6.12 and 2.7.16, matching compiler versions, Axios 0.34.0 and the existing peer stack. Verify CommonJS exports, browser UMD loading/peer externalization, real browser mounts for the shipped components, form validation/submission/error propagation and Axios configuration/interceptors. Compare to a passing baseline. The full fixture matrix in `policy.json` is an **activation prerequisite**, not a claim that it exists or ran during this task.
6. Record the base SHA, tool versions, package-path diff, advisory comparison, install/build/test/lint logs, tarball checksum and fixture results. Recheck the remote base before any authorized push or default-branch integration. On failure, leave the candidate local and report it. On upstream changes, restart from the new base. Never force-push or bypass branch protection.

[npm audit](https://docs.npmjs.com/cli/v11/commands/npm-audit/) reports known vulnerabilities and may leave issues that need manual review. An `npm audit fix` suggestion is not a compatibility gate; avoid unrestricted `npm audit fix` and `--force`. [npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci/) provides the reproducible install step.

## Activation permissions and remaining work

| Stage | Required work and authorization |
| --- | --- |
| Scheduled reporting | Implement/review the runner; authorize a persistent NOVA Task Scheduler job and its reporting destination; provide repository contents and Dependabot-alert **read** access, npm advisory access and local task storage. No remote write token needed. |
| Local candidate preparation | Implement/test policy enforcement and the full consumer matrix; approve individual allowlist entries and unattended worktree creation/install/build/local commits. Keep write/release credentials out of package installation. |
| Future candidate-branch pushes | Explicit **standing** permission for unattended pushes to a named branch pattern, plus repository contents-write access. Current branch-push authorization is a one-time task instruction. No PR permission is sought or needed. |
| Default-branch integration | Explicit permission to apply each reviewed commit, or later a narrowly scoped standing policy for passing allowlisted patches. Require a fresh default-branch SHA, rerun gates and a regular permitted push. Respect protection; do not change access or bypass rules. |
| Package release | Separate approval of the version, generated artifacts, npm publication and any GitHub release/tag. Use an authorized existing publishing credential; any new reusable secret must follow the personal Vault guidance. |

Start with reporting only. Do not enable candidate writes until the runner and fixture matrix enforce every gate and have been demonstrated on both passing and rejected cases. Activation is a separate action from checking in this proposal.

The current local checks used Node 24.19.0 and npm 11.17.0, with `npm ci --ignore-scripts --legacy-peer-deps`. The legacy ESLint peer stack needs the latter option; retain the same install flags for baseline and candidate. Lifecycle scripts were disabled, and the checks exercised this library's JavaScript builds. The unit runner requires a current maintenance Node version; no new runtime engine requirement is imposed on downstream applications. Local installed-tarball fixtures covered Vue 2.6.12 and 2.7.16 with Axios 0.34.0, CommonJS loading and browser UMD in an emulated DOM. Full real-browser and consuming-application checks remain activation prerequisites.

A pushed isolated branch does not clear default-branch alerts: [GitHub scans the default branch](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-alerts). A separately authorized integration is needed for those alerts to reflect the fixes. Older npm consumers also need a separately approved package release and their own dependency/lockfile upgrade. A library lockfile only controls this repository's build; it does not update a consumer's lockfile. Consumers using a Git branch must upgrade to the tested commit and validate their own Vue/compiler/Axios resolutions. Development-only fixes secure the maintainer build/dev tools; runtime dependency changes affect applications.
